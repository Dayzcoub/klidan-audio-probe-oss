## v0.2 high-priority engineering questions
- **Exclusive format matrix implemented in code:** explicit single-endpoint `--scan-formats` performs exact Exclusive format queries once per unique format; `--validate-formats --confirm-exclusive-init` separately performs bounded Initialize-only attempts for each candidate/period with one alignment retry, event readiness and cleanup evidence. It never calls Start or services PCM. Fake API tests cover support/Initialize separation, unsupported/busy results, alignment, period availability, cleanup, JSON schema/privacy and query deduplication. This feature is not hardware validation and does not close the broader 0.2 gate.
- **B1.1 implemented in code:** explicit `--test-init` selects driver-reported default/minimum period, attempts Exclusive event-driven `Initialize` with one alignment retry, then checks buffer size and `SetEventHandle`. Operator results include both Default and Minimum periods; B1.1 does **not** complete v0.2 or the overall 0.2 stage.
- **Operator hardware results (2026-10-29):** Earlier Audient iD4, DEXP U700 and Bloody checks used 48 kHz, 10 ms Default Period and 480 buffer frames. Additional B1.1 runs at 3 ms Minimum Period used 144 frames. None of these results covers `Start`, audio transfer, actual latency or stability; details are in `docs/HANDOFF.md`.
- **Additional B1.1 operator results (2026-10-29):** Audient iD4 Capture PCM16, Capture PCM24-in-32 and Render PCM16; DEXP U700 stereo Capture PCM16; Bloody stereo Capture/Render PCM16 — all `READY`. These checks used 48 kHz, Minimum Period 3 ms, 144 buffer frames, successful Initialize/GetBufferSize/SetEventHandle and no alignment retry. They do not establish `Start`, data transfer or stability.
- **B2/B2.1 implemented in code:** explicit `--test-stream --duration 1..30` runs one Exclusive 48 kHz Stereo PCM16 endpoint, consumes Capture blocks without saving audio or renders silence, reports event interval statistics, discontinuities and post-Start frame coverage. `STREAM_COMPLETED` requires coverage within `max(10% expected frames, 2 × actual buffer frames)`; recoverable anomalies are `STREAM_COMPLETED_WITH_WARNINGS`, and underfeeding fails. Physical B2.1 re-runs remain pending. This does not complete the broader 0.2 stage.
- **B2.2 implemented in code:** `--mmcss off|pro-audio` defaults to off; registration failure blocks Start and there is no fallback. Capture compares each valid device position with the previous packet end, records jump/overlap sizes and correlation with `DATA_DISCONTINUITY`, while excluding `TIMESTAMP_ERROR` packets and resetting its position baseline. The separate quality label is `CLEAN`, `ANOMALIES_PRESENT` or `SEVERE_ANOMALIES`. Severe means the run failed/underfed, a single position delta reached a full actual buffer, or one anomaly class repeated at least three times in one run. A single non-severe anomaly is `ANOMALIES_PRESENT`; no anomalies is `CLEAN`. These thresholds indicate diagnostic severity, not proof of acoustic frame loss. No B2.2 physical test was run in this implementation task.
- **B2.2.1 deadline fix:** Stream duration is measured by `steady_clock`; intermediate bounded wait expirations continue silently, the independent one-second no-event watchdog still fails, API wait errors retain their HRESULT, and operator cancellation cannot complete successfully. MMCSS modes use the same decision path. Automated boundary cases cover sub-millisecond deadline races and watchdog/cancel/API outcomes; no physical test is implied.
- **C1 channel topology and metering implemented in code:** passive Capture inspection reports Windows mix-format channels/mask/labels without assigning physical connectors. `--meter-capture` requires explicit Capture selection and confirmation, is bounded to 1–30 seconds at 48 kHz PCM16 mono/stereo, and reports per-channel peak/RMS/hold/clips through an OS-neutral fixed-storage core. Optional sanitized schema-v1 JSON omits endpoint identity and paths. Tests use synthetic PCM and no endpoint; physical Capture was not tested. Do not infer socket mapping from channel indices.
- **C2 isolated Render channel test implemented in code:** `--test-output-channel` requires an explicit Render endpoint/channel, both live-output and test-signal confirmations, and a 1–10 second timeout; it checks exact 48 kHz Stereo PCM16 support and Initialize before Start. Its OS-neutral no-allocation generator emits a gated 997 Hz sine at no more than −36 dBFS on one Windows channel, with the other channel zero, initial silence and event-driven terminal silence when available. Sanitized schema-v1 JSON excludes endpoint identity and leaves physical mapping `UNKNOWN`. Synthetic tests cover signal behavior, classifier outcomes, JSON privacy and CLI refusal; no hardware test was run. `ReleaseBuffer` is software submission only and does not prove DAC playback or audibility. **Next C3 integration points:** present C1 topology/meter snapshots and C2 Render reports in a shared UI, keeping physical connector mapping explicitly operator-verifiable.
- **D0/D1/D2/D3 GUI status:** Design Kit v0.1 is owner-approved (2026-10-30), ADR-002 accepts WPF .NET 10 + separate native worker + typed local Named Pipe IPC, and D3-B2 provides explicit real Windows endpoint discovery, Exclusive format query, and consent-gated Initialize-only through the GUI. D3-B2.1 organizes that functionality as Device → Test → Result and isolates Local Demo/Worker Fake in Developer Tools. No GUI audio stream is started and no PCM is transferred. Hardware QA and interactive visual/DPI QA remain pending. See [D3-B2 implementation](gui/D3_B2_IMPLEMENTATION.md), [operator workflow](gui/D3_B2.1_OPERATOR_WORKFLOW.md), [architecture](gui/D1_ARCHITECTURE.md), [protocol](gui/D1_IPC_PROTOCOL.md), [lifecycle](gui/D1_LIFECYCLE.md), and [test strategy](gui/D1_TEST_STRATEGY.md).
- **C2 automatic configuration scan — partial implementation:** one explicitly selected active endpoint can run the existing real passive format query and up to four consent-gated 48 kHz PCM16 Initialize-only candidates, then save one aggregated C1 profile. Every result is `INCOMPLETE` for working-configuration purposes because GUI-connected stream Start/servicing, stability, and Duplex are not implemented; no preferred/fallback is emitted. Capture/Render pairing and physical QA remain future work. See [C2 implementation](gui/C2_IMPLEMENTATION.md).
- **C3.5 physical selection and simplified scanner:** normal WPF uses a physical-device selector backed by trusted Windows Container ID metadata, fails closed for missing/ambiguous membership, auto-selects only one confirmed compatible Capture/Render pair, and preserves explicit pairing/technical controls in Developer Tools. The existing Worker-authorized C3.4 scan and persistence path is reused; no physical QA is implied by automated tests. See [C3.5 implementation](gui/C3_5_IMPLEMENTATION.md).
- **B3-A implemented and operator-tested:** explicit `--test-duplex` requires one Capture and one Render endpoint, creates and services each endpoint on its own COM MTA thread, waits for both clients and MMCSS registrations before authorizing Start, and stops the peer on failure/cancellation. Capture data is discarded and Render submits silence. Per-side timing/status/quality and joint overlap/frame-count diagnostics are reported; frame deltas are not clock-drift evidence. Supplied Audient operator evidence is recorded below.
- **B3-A operator evidence (2026-10-29):** Audient iD4 simultaneous Capture/Render passed both 5 s and 30 s at Exclusive 48 kHz Stereo PCM16, Minimum 3 ms, MMCSS Pro Audio. The 30 s run completed/CLEAN on both sides with 100.00%/100.01% coverage, zero long intervals/errors, 0.001 ms Start difference and 30,000.467 ms simultaneous runtime. Frame count differed by 144; Capture had no discontinuities or position anomalies. These operator results do not measure clock drift or RTL. See `docs/DEVICE_QA_NOTES.md`.
- **B3-B implemented and accepted for the tested configuration:** opt-in `--clock-probe` samples each side's `IAudioClock` after servicing, correlates position/frequency with shared QPC timestamps, and estimates each rate slope, relative rate difference and phase change over common time. The bounded fit trims the first four and final sample, requires at least eight points per stream, one second of common span and R² ≥ 0.95. `S_FALSE`, API errors, invalid QPC and nonmonotonic positions are reported distinctly; unreliable/insufficient data produces no ppm estimate. Clock diagnostics do not alter Duplex status or quality. Audient iD4 operator evidence: one 5 s and three 30 s Exclusive Duplex runs, 48 kHz Stereo PCM16, Minimum 3 ms, MMCSS Pro Audio; all `STREAM_COMPLETED` / `CLEAN`, diagnostic `AVAILABLE` / `CLEAN`. The three 30 s relative estimates were 0.0, -0.2 and -0.1 ppm; the 5 s estimate was -1.0 ppm. These results are Windows/driver timestamp estimates, not proof of absolute synchronization, zero hardware drift, 0.1 ppm accuracy, RTL or long-term stability. Details: `docs/DEVICE_QA_NOTES.md`.
- **B4-A implemented and transport-tested on Audient iD4:** explicit `--test-monitor --confirm-live-output` reuses independent Duplex workers and routes transient 48 kHz Stereo PCM16 Capture through a bounded SPSC ring to Render. Software gain is fixed at -24 dB. Prefill is three times the larger actual WASAPI buffer; capacity is eight times that buffer and capped at 64 MiB. Overflow removes oldest frames and records losses; prefill/underrun submits silence. Ring/transport diagnostics and a separate `MONITOR_STATUS` are reported. The 30 s operator test completed cleanly with zero underruns/overflows; signal was audible in one channel. This does not complete the broader 0.4 gate or measure RTL.
- **B4-A.1 signal-level diagnostics implemented and accepted on Audient iD4:** opt-in `--signal-levels` is restricted to `--test-monitor`; it measures Capture before gain/ring and Render after fixed -24 dB, reporting per-channel PCM16 peak/RMS, nonzero/analyzed samples, SILENT flags and zero-data buffers. Operator reported 0 underruns/overflows, `SIGNAL_PRESENT`, Capture L 0.00 dBFS peak / -19.65 dBFS RMS, Capture R -90.31 / -92.02 dBFS, Render L -24.00 / -43.65 dBFS and Render R digital silence; audible signal was confirmed on the left. Input gain will be reduced by the operator. This accepts the checked configuration only; dBFS/channel observations do not prove audibility in general.
- **B4-B1.2 implemented; hardware sequence recheck pending:** retain the 0.80 per-marker diagnostic and add coherent detection using expected marker order, 12,000-frame spacing, signed polarity and missing-marker accounting. Candidate floor 0.35; acceptance uses at least five matches, zero polarity contradictions, mean correlation ≥0.45, spacing deviation ≤24 frames, offset RMS ≤8 frames, coherence score ≥0.12 and a unique-hypothesis margin ≥0.02; candidates must align within 32 frames. B4-B1.1 correlation maxima/candidate reporting, generated/submitted Render PCM counters and centered Capture `QPC = intercept + slope × devicePosition` fit remain in place. Synthetic tests include filtered fractional delay with correlation near 0.59 and adversarial noise, unrelated periodicity, wrong polarity and repeated sequences. The 2026-10-29 Audient observation had 20/20 Render markers submitted, Capture −51.42 dBFS peak/−75.25 dBFS RMS, correlation maximum 0.591447 and five signed candidates spaced by multiples of 12,000 frames; the previous build reported `SIGNAL_NOT_FOUND`. This supports signal presence but is not a measured delay or validation of the new detector. Any `MEASURED` result still requires the existing QPC/clock, continuity, clipping and timing-quality gates. The physical Render→DAC→cable→ADC→Capture estimate is not B4-A Live Monitor latency, driver-only latency or acoustic speaker delay.
- **B4-B1.3 timing gate implemented; operator recheck pending:** three prior Audient iD4 runs reported 19.171981/19.217089/19.167179 ms median delay, with full variation 0.995002/0.064086/0.947528 ms and Capture fit RMS residual 6.731/1.024/12.233 frames. Run 3 also showed early estimates near 19.87 ms, a step to 18.93 ms and later rise to 19.36 ms; Capture rate error was −105.9 ppm. Those `MEASURED` labels came from B4-B1.2 and are not accepted under the new timing gate. B4-B1.3 preserves sequence matches and adds Capture packet residual RMS/max and local interval deviation, Capture/Render clock-fit residual RMS/max, full-set delay range, adjacent jump and fitted trend. Clock max residual includes all valid samples, including warmup/final points used in Render interpolation. At 48 kHz, `GOOD` requires each frame-valued error/spread ≤6 frames (0.125 ms); `WARNING` allows up to 24 frames (0.5 ms); above that or structural timestamp/continuity failures are `UNRELIABLE`. Render interpolation bracket limits are 500 ms / 1 s for GOOD/WARNING. Only GOOD yields `LOOPBACK_STATUS: MEASURED`; no markers or outliers are silently removed. Thresholds express a bounded timestamp/delay error budget rather than device-specific tuning. Synthetic coverage includes clean data, a 1 ms Capture startup timestamp jump, a persistent step, ±100 ppm gradual QPC drift, irregular timestamp errors and Render clock startup/mid-run steps. Physical revalidation is pending; no B4-B2 work is included.
- **B4-B1.4 timestamp detail implemented; hardware correlation pending:** three further Audient iD4 B4-B1.3 runs were Duplex/CLEAN and matched 20/20 markers, but all were `TIMING_QUALITY: UNRELIABLE`. Median delays were 19.178782/19.174060/19.161950 ms; maximum local Capture packet QPC deviations 48.656/47.032/49.620 frames; full delay variation about 1 ms. Capture and Render clock maximum residuals ranged about 0.85–1.43 ms. B4-B1.4 reports the five largest signed Capture packet interval residuals and clock-fit residuals, packet/snapshot positions and times, adjacent clock steps/recovery, and post-run cross-series coincidence with sign/magnitude/time-window details. It separately reports timestamp alignment quality, frame continuity and marker-sequence consistency. No B4-B1.4 physical test was run and no cause is inferred. B4-B1.4 does not change B4-B1.3 timing thresholds, delay calculations or transport; B4-B2 remains deferred.
- **B4-B2A.2 implemented; B4-B2A.3 first-frame handoff implemented, physical recheck pending:** packet-relative synthetic markers are generated after Capture packet service, so their interpolated packet-position QPC is not their acquisition time. Capture packet and Capture IAudioClock position/QPC mappings are independently fitted and compared at common QPC; signed frame-origin offset, local variation, rate agreement and timestamp quality remain distinct. A stable offset is reported without subtraction or absolute-time PASS. Separate software metrics now measure Ring Push completion to the successful Render ReleaseBuffer containing the marker's first frame and the successful ReleaseBuffer containing its fully verified last frame. Each count/distribution and frame pair is reported; incomplete markers are not delivered. Event-driven Exclusive `GetCurrentPadding` is not used as a playback timestamp (Microsoft documents it as typically unnecessary). ReleaseBuffer is submission, not playback. Therefore `MONITOR_LATENCY_STATUS` remains UNRELIABLE for absolute device-time latency; software handoff status is separate. Audient B4-B2A operator results include the earlier 142.674–143.027-frame offset observation and a follow-up run with offset median 142.899 frames, variation 0.544, rate disagreement −0.08 ppm, 20/20 markers, ring loss 0/0, and full-marker software handoff median/min/max 18.0080/17.9731/21.0251 ms. No cause for the frame origin is inferred. Synthetic tests cover independent origins, distinct first/final ReleaseBuffer cycles, damaged/lost continuations, missing QPC and incomplete submissions. No B4-B2A.3 physical test has been run; no result represents DAC playback or physical latency.
- **B4-B2B.1 implemented to Capture-only ARMED preflight; measurement deferred:** the existing `--test-monitor` remains unchanged and is not suitable for the physical return fixture because it routes both interleaved Capture channels to both Render channels. A separate tested router maps Input 1→Render L and hard-zeros Render R, while Input 2 is analysis-only. The new explicitly confirmed `--test-monitor-rtl-preflight` captures only for five seconds, checks the named known PRBS source on Input 1, a quiet Input 2 baseline, clipping and packet/timestamp continuity, then erases bounded memory. ARMED requires at least 99% nominal frame coverage (237,600/240,000 at 48 kHz/5 s), with the remaining 50 ms reserved for stream-edge effects. It never opens/starts Render or writes to the ring; only its synthetic tests have run. It does not measure RTL. For the target Audient iD4 MKII, the vendor lists Input 2 as a JFET instrument input and line output lineup as +12 dBu = 0 dBFS but does not publish a maximum D.I input level; direct Out L→Input 2 remains blocked pending safe level-matching/attenuation review. See `docs/DEVICE_QA_NOTES.md` and `docs/HANDOFF.md`.

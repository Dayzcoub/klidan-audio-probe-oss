# Architecture — independent KLIDAN Audio Probe

## Product boundary
- **Today:** standalone C++20 Windows CLI for endpoint enumeration and Exact Exclusive format inquiry.
- **Future:** diagnostics core, WASAPI Exclusive stream tester, separate WASAPI Shared fallback tester, duplex/loopback analyzer, portable profile/report model, then optional Windows desktop UI.
- **Not:** DAW, live mixer, KLIDAN AudioHost replacement, DSP host, system configuration tool, auto-driver installer or streaming service.

    [CLI] ----------+
                    +--> [Probe core / measurement model] --> [Report / profile JSON]
    [Desktop future]+              |
                                   +--> [Windows WASAPI backend]
                                   +--> [Other backend later only if separately approved]
    [KLIDAN AudioHost] <-- import versioned JSON / runtime revalidation

CLI and UI consume the same core. A device capability **report** records evidence; an operator-selected **profile** proposes initial parameters. A saved profile never bypasses runtime device checks. Hardware identities are local/ephemeral, not global user IDs.

## Transport priority and profile qualification

WASAPI Exclusive is KLIDAN's primary target for professional audio devices. Audio Probe evidence and the resulting device-bound profile are intended to select the minimum stable Exclusive buffer for the exact endpoint and route. A stable profile requires a confirmed minimum search result and all five requested repeatability runs CLEAN, with complete saved and read-back evidence; FAILED or UNKNOWN results are diagnostic only and cannot create a stable device profile. The result only establishes the tested candidate domain and bounded test conditions.

WASAPI Shared is a separate fallback for home game preparation, listening to materials, editing song regions, and watching video when a professional audio device is unavailable. Shared results do not qualify an Exclusive profile, and Exclusive results do not establish Shared behavior. A transport failure or UNKNOWN state does not silently switch modes. Existing AudioHost mode behavior remains as implemented until a separate, explicitly reviewed integration applies a qualified profile; the B5B.6 independent Exclusive diagnostic does not change transport selection or CLEAN criteria.

## Measurement states (MUST be different)
1. Discovered endpoint and device metadata.
2. `IsFormatSupported`: driver claims exact/closest support.
3. `Initialize`: stream initialized successfully.
4. `Start`: stream started.
5. Data delivered/consumed, with event counts.
6. Stable under a bounded measured interval, including errors/underruns.
7. Separate KLIDAN-integration physical acceptance.

Current code implements endpoint discovery, exact-format queries, Exclusive Initialize, bounded single-endpoint stream tests, independent Capture/Render Duplex, opt-in `IAudioClock`/QPC correlation, confirmed PCM16 Capture-to-Render transport, signal-level diagnostics and confirmed physical analog loopback measurement. The B4-B1 mode sends a fixed low-level deterministic marker on one Render channel, retains a bounded selected Capture channel in memory, and erases it after analysis. It maps the marker's Render stream-relative sample index through Render `IAudioClock` position/frequency and paired QPC, then maps captured marker samples through a centered Capture regression `QPC = intercept + slope × devicePosition` on the same QPC scale. Independent start times therefore do not need to match. It reports the whole-recording correlation maximum and sub-threshold candidates separately from marker detections, plus generated/submitted Render PCM counts. B4-B1.2 additionally evaluates sequence-level evidence over known marker order, 12,000-frame spacing and signed polarity; this can identify coherent sub-0.80 candidates but cannot bypass the clock/timestamp, Capture continuity, clipping or timing-quality gates. Missing markers count against coherence, contradictory signs reject a candidate, and close competing alignments are reported ambiguous. Synthetic tests use a low-pass fractional-delay model without assuming a real device filter. This estimates the physical Render→DAC→analog cable→ADC→Capture path and is distinct from B4-A's Capture→Ring→Render monitor delay. Clock-position regression estimates relative stream-position rates only; ring depth is not physical synchronization or RTL. The 2026-10-29 operator run had correlation maximum 0.591447 and coherent-looking signed offsets, but used the prior build and returned `SIGNAL_NOT_FOUND`; the new detector has not yet been physically validated and no latency is measured. Broader sustained-stability validation remains future work.

## Duplex and latency design
- Report capture and render formats/periods/buffers **independently**. Equal buffer size is a **KLIDAN coordinated implementation restriction**, not a universal device property.
- Distinguish requested vs actual frame counts and default/minimum periods.
- Buffer/ring capacity is **not** ring depth or round-trip latency; report each separately.
- Capture/render frame deltas are diagnostic; drift in ppm requires a defensible clock/time measurement.
- Loopback RTL requires actual physical/verified routing and a known stimulus. OS-reported latency is not measured RTL.

## B4-B2B.1 safe routing and preflight boundary

`--test-monitor` retains its original stereo Capture→SPSC→stereo Render behavior; it is not safe for the B4-B2B physical return fixture. The new `MonitorRtlPreflight::StereoStagingBuffer` allocates before audio service and uses a checked transform to stage Input 1 into Render L. It explicitly zero-fills the full staging span before validation/copy, so every Render R sample is zero even on rejected input; Input 2 is never read into a Render sample. B4-B2B.1 unit-tests this transform but does not call it from a live Render worker.

`--test-monitor-rtl-preflight` activates only the Capture endpoint for a bounded five-second capture. It preallocates a six-second in-memory stereo buffer, checks the specified PRBS sequence on Input 1, Input 2 baseline, clipping and capture packet continuity/timestamps, then erases sample storage. It does not configure or push the SPSC ring, request a Render endpoint, or call Render `Start`. `ARMED` requires at least 99% of nominal frames (237,600 of 240,000 in the supported configuration), allowing at most 50 ms for stream-edge effects. Its state machine ends at `ARMED` (or FAILED/CANCELLED); the transition to MEASURING is deliberately unavailable in this phase. A later measurement phase must revalidate the physical/signal preconditions and begin with an explicitly reset empty ring.

The iD4 MKII channel labels follow vendor documentation: rear mic/line is Input 1 and front JFET instrument is Input 2. Vendor data specifies +12 dBu = 0 dBFS line-output lineup but no maximum D.I input level; therefore direct Out L→Input 2 is not approved without a reviewed level-matching fixture. The current preflight cannot establish cable routing, hardware monitor switches or input gain. No physical QA has been performed for B4-B2B.1.

- B4-B1 physical analog loopback uses the same QPC time basis: Render sample frame → `IAudioClock::GetPosition`/frequency → paired QPC; Capture sample frame → packet device position/QPC. Never subtract independent stream frame indices as an absolute delay. If either time mapping fails validation, report `TIMING_ALIGNMENT_UNRELIABLE`, not an estimated success. This is not B4-A live transport delay, driver-only latency, or acoustic speaker delay.
- B4-B2A / B4-B2A.1 / B4-B2A.2 / B4-B2A.3 `--test-monitor-latency` is an explicit five-second synthetic transport run requiring both confirmations before endpoint access. Capture samples are discarded; deterministic low-level markers are generated in preallocated staging only after a Capture packet is serviced, and the existing SPSC carries per-frame provenance. Separate software handoff intervals begin at completion of the Ring Push containing the marker's first source frame: (1) successful Render `ReleaseBuffer` completion for the buffer containing its first frame, and (2) successful completion for the buffer containing its final frame after full marker verification. The tracker preserves source and Render frame indices plus both QPC brackets using fixed-capacity state; it records no marker as delivered until every marker sample is verified and its final ReleaseBuffer succeeds. These intervals measure software scheduling/buffer submission only, not marker acquisition or DAC playback. Capture packet device-position/QPC and Capture IAudioClock position/frequency/QPC series are independently fitted and compared at common QPC; signed frame-origin offset and variation are reported separately from rate difference and local residuals. No constant is subtracted to assert absolute alignment, and absolute device-time latency remains UNRELIABLE without independent origin/playback evidence. The existing 6-frame local residual budget and QPC call bracket checks remain. `GetCurrentPadding` is not sampled: Microsoft says it is typically unnecessary for event-driven Exclusive streams ([GetCurrentPadding](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-getcurrentpadding)). Reports include packet timestamp, synthetic marker generation, Push, first-frame and full-marker ReleaseBuffer QPCs, position-origin diagnostics and all marker provenance outcomes. No analog loopback, ADC/DAC delay or full microphone-monitor latency is measured.
- Active tests are opt-in, time-limited, low-level safe and never auto-run on launch. See TEST_SAFETY.

## B4-B2B.2A offline dual-channel analyzer

`MonitorRtlAnalyzer` is a bounded, OS-neutral, post-capture analysis core with a fixed five-second contract (240,000 nominal frames, at least 99% captured) for 48 kHz PCM16 stereo on one Capture frame timeline. Its expected-frame input must equal the nominal run length; shortening that value cannot relax coverage. It reuses the existing deterministic PRBS marker and coherent sequence detector to pair Input 1 reference markers with Input 2 return markers, then reports signed frame/sample offsets, milliseconds, confidence, missing/ambiguous markers and delay variation. Zero or negative Input2-minus-Input1 offsets reject with an explicit failure; no physical minimum delay is assumed. Its timestamp checks validate packet frame continuity and QPC progression; they do not transform the same-stream sample offset into acoustic or physical RTL. The differential hardware delay between Input 1 and Input 2 is an uncalibrated unknown. `SYNTHETIC_VALIDATED` and `SIGNAL_FOUND` are software/test-fixture evidence only, and `PHYSICAL_RTL_STATUS` is always `NOT_MEASURED`.

Acceptance fails closed for absent or swapped channels, missing/inconsistent PRBS markers, ambiguous sequence, clipping, discontinuity, timestamp/frame gaps, inadequate coverage or excessive variation. Existing timing budgets are retained: GOOD at ≤6 frames (0.125 ms at 48 kHz), WARNING through 24 frames (0.5 ms), and rejection beyond that; only GOOD synthetic cases validate. The dual-channel analyzer has no endpoint or CLI entry point and is exercised only with synthetic PCM.

Routing-isolation tests feed the existing `MonitorRtlPreflight::StereoStagingBuffer` into the unchanged SPSC ring: Input 1 alone populates staging L, staging R is literal zero, and Input 2 is never copied. The tests verify the existing −24 dB gain and 3-buffer prefill behavior, plus silence/error clearing and ring underflow/overflow. They do not enable the route in a live worker.

The future B4-B2B lifecycle is process-local: `IDLE → CAPTURE_PREFLIGHT → VALIDATING → ARMED → REVALIDATING → MEASURING → STOPPING → COMPLETED/FAILED/CANCELLED`. A new process always starts at IDLE; prior `ARMED` state is not an authorization token. Before any future Render start, the operator must revalidate selected endpoints and the physical fixture, explicitly approve output, confirm a fresh empty ring and ready Capture, and establish Render silence. Either worker fault must stop/silence both sides; no generic stereo monitor fallback is allowed. The lifecycle model in this phase is pure/testable and is not connected to Render Start.

For Audient iD4 MKII, the proposed analog return uses line output to Input 2, the front JFET instrument/DI input. Published line-output lineup alone does not establish a safe maximum input level, and vendor specifications do not publish a maximum D.I input level. A reviewed attenuator/level-matching plan and verified cabling are required before any physical return test; this implementation provides no hardware approval.

## B4-B2B.2B disarmed session integration

`MonitorRtlSession::Coordinator` composes the existing lifecycle, Input-1-only `StereoStagingBuffer`, SPSC ring and post-run dual-channel analyzer. Ring Push/Pull, gain and prefill behavior are unchanged; a post-stop erase helper clears PCM/provenance slots after both participants have stopped. The coordinator is an OS-neutral class with no endpoint identity, COM or WASAPI ownership and no CLI entry point. Each coordinator can be configured once; it allocates bounded capture/analyzer packet storage, staging, a fresh empty ring, pull scratch and a fake sink before processing. Ingestion validates packet format, size, position, QPC ordering, continuity and clipping, stores both Capture channels for later analysis, stages only Input 1 to L with R zero, and sends only that staged memory to Ring Push. The harness explicitly calls simulated fake Render pulls; the right output channel is verified after every pull. Input 2 is never offered to the ring.

Readiness fields carry `simulated...` names, a per-session in-process generation, and require explicit harness injection. They advance this session's process-local lifecycle through Capture preflight, validation, ARMED, same-session revalidation and MEASURING; stale readiness from a prior session is rejected. These values are not physical operator approval and cannot be exported or reused as hardware authorization. No Render Start or live worker is connected. After processing stops, bounded frame/transport checks and `MonitorRtlAnalyzer::Analyze` run; results distinguish session, routing, Capture integrity, ring, analyzer, timing and simulation statuses. Failed/cancelled sessions stop accepting packets, silence/discard fake output, erase transient capture/sink/staging storage and release their ring after processing stops. Every outcome keeps `PHYSICAL_RTL_STATUS: NOT_MEASURED`.

## B4-B2B.2C mocked Runtime Safety Gate

`RuntimeSafetyGate::RuntimeSafetyGate` is a separate OS-neutral control model for a future Capture-to-Render authorization boundary. It owns no endpoint, COM/WASAPI object or Render client. Its process-local, non-copyable session identity is referenced by every observation; observations are single-use, sequence-checked, and revalidated against the configured endpoint identity, PCM16 Stereo/48 kHz format, period and actual buffer geometry. Readiness observations distinguish mock/runtime observations from operator declarations; the existing `MonitorRtlSession::SimulatedReadiness` is not convertible to this API. Nothing here serializes authorization.

The checked lifecycle is `IDLE → CONFIGURED → CAPTURE_READY → REVALIDATING → OUTPUT_ARMED → RUNNING → STOPPING → COMPLETED/FAILED/CANCELLED`. `OUTPUT_ARMED` remains output-disabled. The shared start decision only requests both workers; independent, session-local successful start acknowledgements are required from Capture and Render before the fake output sink is enabled. Duplicate, invalid and late acknowledgements fail closed. Revalidation requires both prepared workers, clean Capture continuity/timestamps, initialized/event-ready streams, valid devices, a fresh empty fault-free ring, Input-1-only routing with Render R zero, and explicit per-run operator declarations. Generic stereo monitor routing is rejected. Any worker/runtime fault, cancellation, invalid transition or explicitly reported peer/watchdog timeout inhibits non-silent fake output and requests both workers to stop.

Prepared workers acknowledge quiescence independently. A cleanup attempt while any owner remains active only returns false and stays `STOPPING / WAITING_FOR_QUIESCENCE`; it does not infer a timeout. Resource cleanup cannot complete until every owner is quiescent; acknowledgements and cleanup are idempotent, and diagnostics are retained before cleanup. Statuses always identify `SIMULATION_STATUS: MOCKED`, `HARDWARE_QA_STATUS: NOT_RUN`, and `PHYSICAL_RTL_STATUS: NOT_MEASURED`. A mock declaration cannot verify cabling or electrical safety. No real Render API is added or invoked. Physical output already submitted to a future device cannot be guaranteed to stop instantaneously by this software gate; that limitation must be addressed by the eventual live adapter and operator safety procedure.

## B4-B2B.2D — Capture runtime evidence adapter

The existing explicitly confirmed `--test-monitor-rtl-preflight` path remains the only Capture execution path. `CaptureRuntimeEvidence` records actual selected endpoint/session, PCM16 Stereo 48 kHz format, exact `IsFormatSupported`, Initialize/alignment retry, actual buffer, event setup, Capture service, Start/Stop HRESULTs, packet/frame coverage, timestamp/position integrity, cancellation/watchdog/device invalidation and cleanup. The OS-neutral evaluator maps known facts to a session-bound `RuntimeObserved` CaptureObservation for inspection only; it never creates Render evidence or calls duplex Gate revalidation/start/acknowledgement. Unknown facts stay unknown and a clean result requires the complete five-second Capture plus successful cleanup and validated packet continuity, timestamps and clipping.

The preflight continues using its existing bounded `CaptureData` for PRBS and Input 2 checks. Silent packets with null data are treated as zero without dereference; first device position remains an absolute origin while stored frame offsets start at zero. Packet/QPC anomalies are counted in the preflight collector. The route guard rejects any non-Capture direction, SPSC ring or alternate monitor/loopback path before WASAPI client activation. This mode never activates a Render endpoint, calls `IAudioRenderClient`, pushes to the SPSC ring or authorizes physical output. A diagnostic `CLEAN` Capture report is not duplex authorization, physical RTL, or hardware QA.

## Independent build and future integration
Don't copy the entire KLIDAN audio engine, VST3, PortAudio, games or WPF shell into this repo. The single migrated probe source is a **snapshot**, not a live dependency or auto-sync. Track upstream changes consciously and cite their commit.

For interoperability, define versioned JSON and validation before any KLIDAN-side import. **No source-level or runtime dependency** on this executable; any future shared library requires its own architectural review.

The eventual macOS / CoreAudio or ASIO backend is a potential extension, not a v0.x requirement; keep semantic profile/report definitions free of Windows COM interfaces.
